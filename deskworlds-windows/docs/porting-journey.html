Porting notes / macOS to Windows

How a Mac-only desktop wallpaper got a Windows version

The project is chaseleantj/deskworlds: four live 3D worlds (Riverbed, Coral reef, Betta, Plasma globe) that run as a wallpaper on macOS. Porting it looked like a big job. It turned out to be a small one, because almost none of the code is Mac code. This page walks through what was actually ported, in the order it happened, including the parts that went wrong.

Scenes unchanged, byte for byte C# host builds on Windows CI Scene tests pass on Windows CI Desktop attach not yet run on a real laptop

The short version

A wallpaper app has two halves. One half draws the picture. The other half puts a window in the right place on the desktop and tells the picture what the user is doing. In Deskworlds the drawing half is JavaScript and WebGL, which runs in any modern browser, so it needed no porting at all. The second half was written in Swift for macOS. That is the only part that had to be rewritten, and it is the part this page is about.

macOS host, Swift (left behind)656

Lines counted with wc -l. Bars share one scale. The C# host is longer than the Swift one mostly because Win32 calls need a declaration for each function, which Swift gets for free from Apple's frameworks.

First question: is this an Xcode project?

No, and that matters for anyone thinking about a port. There is no .xcodeproj, no storyboard and no build settings to untangle. The installer, wallpaper/install.sh, compiles one file with a single command:

swiftc -O -target "$(uname -m)-apple-macos13.0" -o Deskworlds Wallpaper.swift \
  -framework Cocoa -framework WebKit -framework IOKit

Xcode is not involved. The installer only needs Apple's command line tools for the swiftc compiler. So there was nothing to convert. The work was to read one 656-line file, list every job it does, and find the Windows way to do each job.

Where the desktop layers sit

The core trick of a desktop wallpaper app is to place its window between two things that already exist: your normal wallpaper picture and your desktop icons. Both systems allow this. They just do it differently.

The journey, step by step

  1. Check that the port is even needed

    The README said it plainly: "The desktop app supports macOS only. The browser preview needs a browser with WebGL2." That second sentence is the key. The project already ran in a browser on any operating system, so the scenes were portable by design. I cloned the repo and ran its own checks (npm run check and npm test) on Linux. They passed, which confirmed the scenes do not depend on macOS.

    LessonBefore porting anything, find out which parts already run somewhere else. Here, that was about 96% of the code.

  2. Find the seam between the host and the scenes

    The two halves talk through a tiny interface. I searched the Swift file for every place it calls into the page and found exactly five function names. The scenes define three of them. The host defines the pointer pair itself, by injecting a script.

    CallSent by host whenWhat the scene does
    sceneRate(fps)Visibility or power changesSets the frame rate; 0 stops drawing
    scenePower(onBattery)Plugged in or unpluggedSwitches to a lighter quality profile
    sceneFeed()Feed clicked in the menuDrops food into the scene
    scenePointer(x, y)The cursor movesCreatures react (host-injected shim)
    scenePointerOut()The cursor leavesCreatures stop reacting (host-injected shim)

    There is one more piece: a "ready" message the page sends once it has installed those functions, so the host does not talk too early. That interface is the whole contract. Anything that can call five JavaScript functions can host these scenes.

    I went through the Swift file top to bottom and wrote down every job. For each one I asked "what does Windows call this?" Most had a direct answer.

  4. Solve the hard one: get behind the icons

    This is the one part with no clean public API. On Windows the desktop is made of windows owned by Explorer. The icons live in one, called SHELLDLL_DefView. The wallpaper picture lives in another, called WorkerW. A well-known trick is to send Explorer's Progman window the undocumented message 0x052C, which makes it create a WorkerW you can attach to. Then you make your own window a child of it.

    The catch, as other wallpaper projects report, is that Windows 11 24H2 rearranged this tree. I could not confirm that here, so the port checks for both layouts:

    var defView = FindWindowEx(progman, IntPtr.Zero, "SHELLDLL_DefView", null);
if (defView != IntPtr.Zero)              // Windows 11 24H2 and later
    return new Slot(progman, defView);   // sit just below the icons

// earlier builds: the WorkerW that follows the icons' WorkerW
worker = FindWindowEx(IntPtr.Zero, top, "WorkerW", null);

    A child window is positioned in its parent's coordinates, and the parent spans all monitors, so a monitor to the left of the main one has a negative origin. The code converts each monitor's rectangle with ScreenToClient before placing the window.

    RiskThis mechanism is undocumented and has changed between Windows releases. It is the most likely thing to need a fix on a real laptop, and it is exactly what I could not test from a Linux sandbox. The --window flag exists so you can tell an attach problem from a scene problem.

  5. Read the workaround comments, they are a map of the traps

    The Swift file has a comment explaining that WebKit stops drawing a page whose window it believes is covered, and a background agent's window always looks covered. So the original author switches that detection off and works out what is really covered by hand.

    Chromium, the engine inside WebView2, has the same behaviour under a different name. A window sitting behind the desktop icons would look permanently hidden and the scene would never start. The fix is one startup flag, --disable-features=CalculateNativeWinOcclusion, plus a few that stop background throttling. I would not have known to look for this without the Swift comment.

    LessonComments that explain a strange workaround point at platform behaviour that will bite again on the next platform. Grep the source for them first.

  6. Deliver the mouse without receiving the mouse

    The wallpaper window must never take clicks, or you could not use your icons. So it never sees the cursor either. Both the original and the port solve this the same way: a timer reads the global cursor position, then calls scenePointer(x, y) in the page.

    The one Windows-specific pitfall is units. GetCursorPos returns physical screen pixels, but the page thinks in CSS pixels. On a laptop set to 150% scaling those differ by a factor of 1.5. The port sets the process to per-monitor DPI awareness in its manifest and divides by the window's DPI scale, so a creature follows the cursor and not a point 50% off from it.

  7. Serve the files like a web server would

    The scenes use ES module imports, and the reef loads its rock meshes with fetch. Both fail from a plain file:// address. macOS solves this with a custom URL scheme. WebView2 has a neater tool: map a fake host name to a folder, so the page loads from https://deskworlds.local/scenes/riverscape/wallpaper.html while the bytes come from disk. Nothing touches the network.

    One more small bridge: the original page announces itself with window.webkit.messageHandlers.ready, which only exists in Apple's WebKit. Rather than edit the scene loader, the host injects a two-line shim before the page runs that forwards the same call to WebView2's chrome.webview.postMessage. The scene code stays identical.

  8. Copy the power policy exactly

    The original decides how hard to draw from what is visible: 60 fps when the desktop is clearly showing, 30 on battery, 20 when mostly covered, and stopped when almost fully covered, locked, asleep or in low-power mode. It samples a 16 by 10 grid of points to estimate how much of a monitor is uncovered.

    I kept every number. Only the questions changed: "which windows are on screen" now comes from EnumWindows, ignoring hidden, minimised, tool and "cloaked" windows (those on other virtual desktops), and "am I on battery" comes from GetSystemPowerStatus. Keeping the behaviour identical made the port easy to check against the source.

  9. Rebuild the plumbing: tray, settings, install

    The menu became a tray icon with the same items (World, Feed, Pause, Quit) plus a Start with Windows toggle. Saved choices became a small JSON file. install.sh became install.ps1: it publishes the C# app for the machine's CPU, copies the scenes next to it minus their test folders, adds the sign-in registry value and starts the app. npm run check also had to be rewritten, because it used a Unix shell loop that does not run under Windows' cmd.

  10. Prove it works without a Windows machine

    The sandbox where I worked runs Linux, and the .NET SDK there cannot build Windows desktop apps. So the proof came in two layers:

    • Compile check here. I compiled the C# against Microsoft's real WinForms and WebView2 reference assemblies from NuGet. This catches typos, wrong types and missing methods, but runs nothing.
    • A real Windows build in CI. A GitHub Actions workflow on windows-latest runs the scene checks and tests, builds the app self-contained, bundles the scenes and uploads the result. Both runs came back green.

    That is strong evidence the code builds and the scenes work on Windows. It is not evidence that the wallpaper attaches behind the icons on your screen. Only running it can show that.

Scene by scene

Since every scene is unchanged, "porting each scene" comes down to what the host does differently for each one. I checked with diff -r: the scenes, vendor (Three.js) and ui folders are identical to the original.

All four pages set data-motion="host", which is the switch that tells the scene to wait for the host's rate and power messages instead of running itself.

What went wrong along the way

Wrong assumptions and blocked tools

The obvious .NET installer download was blocked by the sandbox's network proxy, so I used the operating system's package manager, which first needed a package index refresh after a 404. Even then the Linux .NET SDK has no Windows desktop targets, which forced the reference-assembly trick above. Separately, my first pull request used main as its base branch, but the repo's default branch has a different name, so GitHub rejected it until I looked it up.

A real bug caught by re-reading

In my first draft the controller started the browser engine's asynchronous setup from its constructor, which runs before the Windows message loop exists. Continuations after an await would then have landed on a background thread, where WebView2, which must be used from the UI thread, does not work. I moved the start into a message posted to the UI thread. The compile check could not have caught this, because the code was valid, just wrong at runtime. This is the class of mistake that only a real run, or a careful read, finds.

A stuck command

I left a stray cat with no input in a shell command. It waited forever and timed out. Nothing was lost, but the workflow file and ignore file had to be written again.

Terms used above

WebView2
Microsoft's embeddable version of the Edge browser engine. Windows' counterpart to macOS's WKWebView.
Progman and WorkerW
Windows Explorer's own windows that make up the desktop. Progman is the top one; WorkerW windows can hold the wallpaper picture.
P/Invoke
How C# calls a Windows system function. Each function is declared once with its exact signature, which is why the C# is longer than the Swift.
DPI scaling
Windows can draw at 125%, 150% or more so text is readable on dense screens. Physical pixels are the real ones; CSS pixels are what a web page counts.
Self-contained publish
A .NET build that bundles the .NET runtime, so the person running it does not have to install .NET.
Cloaked window
A window Windows keeps alive but hides, for example one on another virtual desktop. It must not count as covering your wallpaper.
